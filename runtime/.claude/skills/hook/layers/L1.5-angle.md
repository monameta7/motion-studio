## 🧩 Layer 1.5 — موتور زاویه محتوا

**چرا مهم است:** هوک از **زاویه** می‌آید. اگر زاویه‌ی محتوا تکراری و بی‌تمایز باشد، تکنیک هوک به‌تنهایی آن را نجات نمی‌دهد؛ اما تکرار موضوع یا زاویه بدون بررسی نمونه و عملکرد، دلیل کافی برای رد ایده نیست.

### 1.5.0 — ورودی الهام (فقط وقتی ورودی محتوای دیگری را می‌دهد)

اگر کاربر ریل، پست، مقاله یا ایده‌ی سازنده‌ی دیگری داده: **قانون بازسازی الهام (ب۱–ب۵، `references/publish-rules.md` بخش ۳)** همین‌جا اجرا می‌شود.

```
اسکلت منبع:  ایده‌ی مرکزی: … · مکانیزم: … · ساختار: …
زاویه‌ی منبع: …            ← به‌عنوان زاویه‌ی منبع ثبت می‌شود و عیناً انتخاب نمی‌شود؛ این ثبت به‌معنای اشباع کل نیچ نیست
جزء تازه‌ی ما: …           ← مدرک خام / مثال محلی / گام عملی / خطای ناگفته
اعتبار صاحب ایده: …        ← نام، اگر داده یا کشف مال اوست
```

زاویه‌ی منتخب (1.5.3) نباید زاویه‌ی منبع باشد. آزمون بازسازی و استقلال در Layer 9 بند ۱۷ اجرا می‌شود.

**ضدتکرار خودی (ب۵؛ در صورت وجود داده):** اگر لاگ انتشار در دسترس است، چند انتشار اخیرِ قابل‌مقایسه را بررسی کن. تکرار یک زاویه یا قالب را به‌عنوان نشانه‌ی یکنواختی ثبت کن، نه ممنوعیت خودکار؛ با توجه به عملکرد و هدف، در صورت نیاز جایگزین پیشنهاد بده. بی‌لاگ یا داده‌ی کم → `[داده‌ی کافی برای قضاوت نیست]`؛ اشباع را حدس نزن.

### 1.5.1 — زاویه‌های اشباع‌شده
اگر نمونه‌های پیج، تحقیق یا محتوای رقبا در دسترس است، زاویه‌های پرتکرار را ثبت کن. بدون شواهد، آن‌ها را «اشباع» یا ممنوع اعلام نکن؛ می‌توانی فقط به‌عنوان فرضیه علامت بزنی.
مثال نیچ AI: «۵ ابزار AI که باید بشناسی» · «AI شغلت رو می‌گیره» · «ChatGPT رو اینجوری پرامپت بده»

### 1.5.2 — ساخت زاویه‌های جایگزین در صورت نیاز

| زاویه | تعریف | نمونه |
|---|---|---|
| **درد** | مستقیم به درد پنهان می‌زند | «چرا هر بار می‌خوای شروع کنی، عقب می‌ندازیش؟» |
| **تضاد** | باور رایج را می‌شکند | «مشکل تو کمبود ایده نیست؛ نبود سیستمه» |
| **راز/پشت‌صحنه** | چیزی را نشان می‌دهد که معمولاً دیده نمی‌شود | «چیزی که تو کارگاه‌ها بهت نمی‌گن» |
| **نتیجه** | از خروجی نهایی شروع می‌کند | «این روش زمان انجام کار رو کمتر کرد» |
| **کشف** | یک علت، قاعده یا واقعیت کمتر دیده‌شده را آشکار می‌کند | «چرا افزایش سرعت همیشه زمان زیادی ذخیره نمی‌کنه؟» |
| **مقایسه** | دو انتخاب یا موقعیت را با معیار مشخص می‌سنجد | «کدوم روش واقعاً زمان کمتری می‌گیره؟» |
| **آزمایش/تست** | یک ادعا را با آزمون واقعی بررسی می‌کند | «این ابزار رو با کار واقعی امتحان کردیم؛ نتیجه چی شد؟» |
| **پیامد** | هزینه یا نتیجه‌ی یک تصمیم را نشان می‌دهد | «این چند دقیقه صرفه‌جویی چه ریسکی ایجاد می‌کنه؟» |

### 1.5.3 — انتخاب زاویه منتخب
```
زاویه منتخب: ... · دلیل: ... · وضعیت تکرار/اشباع: [شاهد داریم / تکرار دیده شد / داده کافی نیست] · تصمیم: [ادامه / تمایز بیشتر / جایگزین]
```

### 1.5.4 — ترجمه‌ی اجباری Feature → Outcome (قدم قفل‌شده)

مخاطب معمولاً فقط نام قابلیت را نمی‌خواهد؛ می‌خواهد بداند آن قابلیت چه نتیجه یا تغییری برایش ایجاد می‌کند.

```
Feature (چیزی که تو داری):        ...
Outcome (چیزی که مخاطب می‌خواهد): ...
پل اتصال:                          Feature → نتیجه‌ی میانی → Outcome نهایی
```

```
Feature: سطح مقطع واقعی مس در کابل
Outcome: «کابلی که زیر بار داغ نمی‌کنه»
پل: سطح مقطع کمتر → مقاومت بالاتر → گرما → خطر آتش‌سوزی
✅ «چرا این سیمِ نو، زیر بار داغ می‌کنه؟»
❌ «امروز درباره سطح مقطع کابل حرف می‌زنیم»
```

**تست شکست:** اگر هوک از جنس «امروز می‌خوام درباره [Feature] حرف بزنم» بود → فِیل.

**قانون:** هوک اصلی Layer 2 باید از دل **زاویه‌ی منتخب + Outcome** بیرون بیاید، نه از موضوع خام. اگر کاربر گزینه‌ی جایگزین خواست یا تست چندزاویه‌ای تصمیم را روشن می‌کند، ۲ تا ۳ گزینه‌ی واقعاً متفاوت بساز؛ تعداد و زاویه‌ها به نیاز بستگی دارد و سهمیه‌ی اجباری نیست.
